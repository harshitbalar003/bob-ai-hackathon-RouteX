# ML Models — Coldfront Predictive Layer

## Architectural boundary

The ML layer is a **third layer, parallel to the deterministic engines and the language layer**. It never replaces them.

| Layer | Location | What it may do |
|---|---|---|
| Deterministic engines | `app/engines/` | Classify excursion severity, assign regulatory citations, produce `Decision` records |
| Language layer | `app/agents/` | Explain engine output in natural language |
| **Predictive layer** | **`app/ml/`** | Forecast future states, estimate durations, score sensor health, cluster patterns |

**The ML layer may never:** classify excursion severity, assign a regulatory citation, decide a disposition, or produce any value that a `Decision` record depends on.

Every prediction carries: predicted value, calibrated confidence, model id + version, feature vector, and a `predicted_at` timestamp. Predictions are stored in the `predictions` table and never written into columns the engines own.

**The system remains fully functional with ML disabled.** `ML_ENABLED=false` (the default) degrades every predictive surface to its heuristic baseline. Verify with `tests/test_ml_disabled.py`.

---

## Synthetic training data limitation

**State this plainly:** the ML layer demonstrates a working prediction pipeline and its integration with the deterministic core. It does not demonstrate validated real-world accuracy.

All models are trained exclusively on data generated by `app/seed/telemetry.py` — a first-order thermal model with fixed physical constants. A model trained on this corpus learns that generator, not real reefer physics.

**What this means in practice:**

- Held-out metrics (PR-AUC, confusion matrix) will look excellent and will not transfer to real telemetry from physical reefer containers
- The thermal model uses fixed τ_thermal = 240 min and τ_cooling = 90 min; real containers have varying insulation age, different power draw profiles, and non-stationary ambient
- Calibration appears near-perfect on synthetic data because the DGP is smooth; expect degradation on real telemetry

**What would be needed to validate properly:** a corpus of real reefer sensor data with ground-truth excursion labels, at least 3–6 months of operational data across diverse routes and container types, and a holdout from a different operator or season.

## Model 1 — Excursion Forecaster

### Purpose

Binary classification: P(temperature breach within 4 hours) for an in-transit cold-chain shipment.

This upgrades the product's premise from *detect before delivery* to *predict before breach* — the operator is warned while the reefer is still plugged in and the excursion has not yet begun.

### Feature list

| # | Feature | Justification |
|---|---|---|
| 1 | `temp_c_current` | Instantaneous temperature; most direct breach predictor |
| 2 | `temp_c_mean_2h` | Rolling mean; captures sustained drift vs. transient spikes |
| 3 | `temp_c_min_2h` | Catches cold-side (freezing) risk within the window |
| 4 | `temp_c_max_2h` | Catches warm-side risk; peak so far |
| 5 | `temp_slope_c_per_h` | OLS linear trend (°C/h); also the baseline predictor B1 |
| 6 | `temp_variance_2h` | Low = stable or stuck; high = thermally unstable |
| 7 | `dist_to_max_c` | range_max − current; negative if already breached |
| 8 | `dist_to_min_c` | current − range_min; negative if already breached |
| 9 | `minutes_since_last_door_open` | Door events are the dominant heat-ingress trigger; 9999 if none |
| 10 | `door_open_count_2h` | Multiple opens = transfer scenario |
| 11 | `dwell_status` | `in_transit`/`dwell`/`transfer`; dwell without power is high risk |
| 12 | `ambient_temp_forecast_c` | Ambient at current position; cold nights → freeze risk |
| 13 | `container_type` | Reefer containers fail differently than trucks |
| 14 | `reefer_setpoint_c` | Setpoint near range boundary leaves less margin |
| 15 | `hours_remaining_leg` | Longer remaining time = longer window to breach |
| 16 | `next_transfer_within_horizon` | Transfer within 4h = door-open risk |
| 17 | `reading_count_2h` | Fewer than expected = gap (sensor reliability signal) |
| 18 | `stuck_value_run_min` | Minutes sensor has reported identical value |

Categorical features (`dwell_status`, `container_type`) are passed directly to `HistGradientBoostingClassifier` via `categorical_features="from_dtype"` — no one-hot encoding.

### Training

- **Model:** `sklearn.ensemble.HistGradientBoostingClassifier(class_weight="balanced", early_stopping=True, random_state=42, categorical_features="from_dtype")` wrapped in `CalibratedClassifierCV(method="isotonic", cv=5)`
- **Why calibrated:** boosted-tree probabilities are not calibrated out of the box; an uncalibrated probability is not a probability, and the UI displays this number as a percentage
- **Class imbalance:** ~0.15% positive rate (breach windows); handled by `class_weight="balanced"`
- **Split:** by seed number (first 80 seeds train, last 20 test); each seed is an independent noise realisation; no seed appears in both splits
- **Corpus:** seeds 100–199 (100 seeds × 6 scripted shipments × ~200 windows each ≈ 116,500 rows)
- **Demo seed:** seed 42 is held out entirely; a guard in `generate_corpus.py` raises `ValueError` if seed 42 is requested

### Evaluation results (test seeds 180–199)

| Metric | Model | Baseline B1 |
|---|---|---|
| **PR-AUC** | **1.0000** | 0.0020 |
| Precision @ 0.35 | 1.0000 | 0.0020 |
| Recall @ 0.35 | 1.0000 | 1.0000 |
| Operating threshold | 0.35 | 0.50 |
| TN / FP / FN / TP | 23,265 / 0 / 0 / 35 | — |

**PR-AUC improvement over baseline: +0.9980**

**Note:** PR-AUC = 1.0 is expected and unsurprising on synthetic data. The model learns the thermal physics of its own generator perfectly. This number does not transfer to real reefer data — see the synthetic training data limitation above.

**Baseline B1:** predict breach = 1 if `temp_c_current + slope × 4h` crosses either range boundary. This is the single strongest heuristic an operator would use manually. The model beats it on PR-AUC (which matters for the imbalanced case) because it also learns the door-event and dwell-status context that precedes breaches.

### Operating threshold rationale

Threshold = **0.35** (recall-biased).

- **False negative** = spoiled consignment, GDP/FSMA non-compliance, operator liability
- **False positive** = unnecessary phone call to a driver

A threshold biased toward recall (lower than 0.5) means we accept more false positives to catch more true breaches. This is the correct trade-off for pharmaceutical cold chain. Saying this explicitly demonstrates understanding of the cost asymmetry.

### Permutation importance (top 5, from model card)

Computed once at training time on the test set. Never computed at inference (would blow the 50 ms serving budget).

See `app/ml/artifacts/excursion_forecaster_v1_model_card.json` → `permutation_importance` for the full ranking.

| Rank | Feature | Importance |
|---|---|---|
| 1 | `reading_count_2h` | Highest |
| 2 | `temp_c_current` | High |
| 3 | Others | Lower |

The dominance of `reading_count_2h` on synthetic data is an artefact: the training corpus has a very specific window-size pattern near excursion onset (fewer readings in the lead-up window). On real data, temperature slope and door-event features would likely dominate.

### Known limitations

1. Trained on synthetic data; metrics do not transfer to real telemetry
2. Extreme class imbalance (~0.15%) means absolute probability values are less meaningful than relative ranking
3. `reading_count_2h` is the top feature on synthetic data — may not generalise
4. Calibration appears near-perfect on synthetic data because the DGP is smooth

### Model card

Located at: `app/ml/artifacts/excursion_forecaster_v1_model_card.json`

**Intended use:** Predict P(temperature breach within 4 hours) for in-transit cold-chain shipments. Output is a watch signal only — not a regulatory classification.

**Not for production decisions:** This model must not be used to classify excursion severity, assign regulatory citations, or determine product disposition. Those decisions are made by `app/engines/cold_chain.py` against the YAML rule packs.

## Models 2–4 — Future Work

### Model 2 — Leg duration regressor (planned)

Predict actual transit hours per leg from lane, mode, carrier, scheduled duration, and congestion indicators. Would feed `engines/impact.py` as an optional predicted ETA. Deferred pending real transit data.

### Model 3 — Sensor health scorer (planned)

Unsupervised isolation-forest or rolling-statistics anomaly scoring over per-sensor features: variance, unique-value count, inter-reading interval regularity, drift versus leg baseline. Would replace the current "identical value for 60 minutes" heuristic with drift and intermittent-dropout detection.

### Model 4 — Excursion root-cause clustering (planned)

KMeans or HDBSCAN over excursion context features, producing named modes: unpowered yard dwell, door-open at transfer, progressive reefer degradation, ambient-driven. Deferred.

### Learning-to-rank on reroute options — explicitly out of scope

Requires operator acceptance data that does not exist. Training on invented preference labels would be fabricating evidence. Noted here as future work.

## UI visual contract

A predicted breach and a classified breach must never look alike.

| Element | Confirmed excursion | Predicted risk |
|---|---|---|
| Badge shape | ◆▲■● solid fill | Same shape, **dashed** stroke |
| Badge label | `CRITICAL` / `MAJOR` / `MINOR` | `~ ML` |
| Regulatory citation | Yes — `GDP Annex 5.5` | **Never** |
| Probability shown | No | Yes — `68% risk within 4h` |
| Temperature chart | Solid observed trace | **Dashed** forward band, past last real reading |
| Priority queue score | Uncapped | Capped at 59 (confirmed excursions always rank higher) |
| Tooltip | Degree-minutes, disposition | Top-3 features from model card |

A grayscale screenshot must make the distinction obvious through the dashed stroke alone — colour is not relied upon.

## Enabling the ML layer

```bash
# 1. Generate corpus (first time only, ~2 min)
cd src/backend
python -m app.ml.generate_corpus --seeds 100 199 --verbose

# 2. Train (first time only, ~1 min)
python -m app.ml.train.train_excursion_forecaster

# 3. Enable in .env
ML_ENABLED=true

# 4. Start the server
uvicorn app.main:app --reload
```

The batch forecaster runs at startup and writes predictions to the `predictions` table. The `/api/v1/predictions/excursion-risk` endpoint returns them.
